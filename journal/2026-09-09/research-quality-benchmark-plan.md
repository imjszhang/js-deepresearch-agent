# 可核验调研质量评测：实施计划

日期：2026-09-09。状态：待实施；本轮只制定计划，没有修改程序、建立标准答案或启动真实调研。

## 1. 目标与范围

建立能回答以下三个问题的评测体系：

1. 报告有没有回答应当回答的问题，事实、条件和引用是否正确？
2. 错误发生在发现来源、读取、提取、判断、绑定还是报告表达阶段？
3. 同样配置与预算下，一次系统修改是否带来可复核的改善？

首轮使用 Redis 许可证演变、SQLite WAL 两个主题，各有明确任务版和开放探索版，各重复两次，共 8 次真实探索性调研。Python 自由线程作为后续迁移验证主题，首轮不加入。

本计划的实现以独立评测、结果诊断、基线运行和修复清单为交付。不要在建立基线时同步重写调研算法；实际算法修复从基线揭示的问题另行实施。Open Science 可保留为资料稀疏场景，不纳入本轮主分数。

## 3. 题目设计与版本冻结

### 3.1 Redis：版本边界与冲突裁决

对象限定为 Redis 核心 7.2.0、7.4.0、8.0.0，比较 Redis Stack 和商业产品时明确它们是不同对象。冻结截止日期为 2025-05-31；正式冻结前核对对应 release、tag、LICENSE 路径和发布日期。

明确任务版：

> 截至 2025 年 5 月 31 日，调研 Redis 核心 7.2.0、7.4.0、8.0.0 的许可证变化。分别列出每个版本提供的许可证选项，区分核心项目、Redis Stack 和商业产品，解释不同时间官方公告中看似矛盾的说法。用对应版本的许可证文件和公告支持结论。仅讨论许可证事实，不推断某家企业具体使用方式是否合法。

开放探索版：

> 截至 2025 年 5 月 31 日，调研 Redis 从 7.2 到 8.0 的许可证演变，以及理解这些变化时容易混淆的地方。

拟设 20 个原子评分点，按以下分组建设，最终答案须逐项取证后冻结：

- 版本与许可证选项：6 项。
- 选项之间的关系、对象及版本适用范围：4 项。
- 公告时间线、旧公告的适用边界与冲突解释：5 项。
- 核心、Stack、商业产品的区分：3 项。
- 未经证据支持的合规推断及不确定性边界：2 项。

重点错误样本：把当前许可证覆盖旧 tag；把多个可选许可证说成同时必须接受；混淆模块和核心；把旧公告直接标成假信息；保留反证却无处置说明。

权威入口：Redis 官方许可证页面、各版本仓库 LICENSE、2024 年许可变更公告和 Redis 8 发布公告。动态总览页用于发现，不能替代冻结 tag 的历史证据。

### 3.2 SQLite：条件、机制与建议

固定 SQLite 3.46.0、单机本地文件系统、多个独立连接/进程、WAL 模式。该版本是拟选实验基准，实施时必须核实可取得的源码、版本化文档与校验值后冻结；不能混入后来版本新增行为。

明确任务版：

> 针对 SQLite 3.46.0，一个单机服务在本地文件系统上使用 WAL，多个独立进程访问同一数据库，有长时间读取和持续写入。调研读写并发限制、SQLITE_BUSY 与 SQLITE_BUSY_SNAPSHOT 的相关场景、长读事务对 checkpoint 和 WAL 增长的影响，以及运行中可靠备份的方式。说明建议的前提，区分文档确认的机制、依赖配置的行为和仍需实验验证的判断。

开放探索版：

> 调研 SQLite 3.46.0 在单机本地文件系统、多个进程访问、长时间读取和持续写入场景中的 WAL 可靠性风险及应对办法。

拟设 20 个原子评分点：

- 读写并发及快照边界：4 项。
- 写锁竞争、快照升级和忙碌处理：4 项。
- checkpoint 模式、读事务及 WAL 增长关系：5 项。
- 运行中备份、文件状态与恢复条件：5 项。
- 建议的条件和实验能证明的边界：2 项。

重点错误样本：把读写并发解释为并发多写者；把 busy_timeout 写成所有 BUSY 的通用解法；把自动 checkpoint 阈值写成硬上限；把运行中只复制主数据库文件说成普遍可靠。

权威入口：SQLite WAL、Isolation、Checkpoint、Online Backup、VACUUM INTO 的官方文档及对应版本源码。当前官网新增内容只有经版本核对后才能作为该题事实依据。

### 3.3 两种问法如何公平评分

- 两版共享事实真值、版本范围和核心评分点，使其覆盖率可以比较。
- 明确版单独计算原文明示交付项完成率；每个交付项保留原文位置。
- 开放版的隐藏要点衡量探索覆盖，不转化为 ResearchRequest 的 required slots。
- 核心要点权重 2，一般要点权重 1，在看到被测输出之前冻结。某项到底属于核心还是附加发现必须在题库中预先标明。
- 额外正确发现单列，不抵消核心遗漏；不要求固定篇幅或来源数量。
- 两题适合调试机制，不能代表全部领域的研究能力；后续需要不同领域和资料稀疏题验证泛化。

## 4. 独立标准答案与证据包

每题包含两部分，运行进程只能得到第一部分：

1. 公开运行定义：caseId、query、语言、版本/日期、配置、重复次数。
2. 评测专用包：原子答案、有效证据、常见错误、冲突裁决、评分细则及人工复核记录。

每个评分点至少包含：

| 字段 | 用途 |
|---|---|
| `criterionId / topicId / rubricVersion` | 稳定身份与版本 |
| `expectedAnswer / scope / qualifiers` | 原子事实、对象、日期、版本和必要条件 |
| `weight / critical / criterionType` | 权重、重大项、事实或综合推理类型 |
| `explicitRequirementSpan` | 仅明确版可有，关联题目原文；开放版不得伪造 |
| `acceptableEvidence / alternatives` | 标准证据及等价证据接纳规则 |
| `commonErrors / conflictCases` | 反例和预期裁决，不使用简单关键词否定 |
| `goldAnchors` | URL、仓库 commit/tag、抓取时间、正文 hash、提取器版本、UTF-16 区间 |
| `reviewStatus / reviewHistory` | 草稿、已核验、待裁决；保留修改理由 |

建设步骤：收集原始证据 → 拆分原子答案 → 检查同一来源及跨来源冲突 → 独立复读关键原文 → 运行 SQLite 实验 → 冻结题库版本和哈希。

LLM 可辅助起草，但不能以同一模型的另一段回答充当标准答案。由实施者对全部评分点逐项对照原文核验；对所有重大项、冲突项及自动裁判争议项进行人工复核。没有人工复核的批次只能标为机器评估草案，不能宣传为人工确认结果。

接受有效的新证据；如果它改变标准答案，必须升级 rubricVersion 并重评全部相关输出，不能只改候选版本得分。对可接受证据的补充也保留记录。一个官网的多篇文章不自动等于多个独立来源。

公开材料快照放在本地评测目录，不提交整页正文。仓库提交题目定义、schema、核验清单和安全的证据索引；评测答案及快照不加入本地检索 corpus、planningContext、模型 prompt 或运行工作目录的可检索范围。限制被测接口的数据访问，不声称仅靠目录命名就实现安全隔离。

## 5. SQLite 独立实验裁判

使用固定版本 SQLite 的测试程序，在临时目录建立新数据库。显式记录 SQLite 版本、编译选项、journal_mode、synchronous、busy_timeout、连接与事务边界。避免用当前 Node/Python 内置的不同版本冒充固定基准。

至少实现以下四个实验：

1. **两个写者竞争**：通过进程间握手确保事务重叠，检查写者串行化及返回码。
2. **旧读快照升级写事务**：先建立读快照、另一连接提交，再尝试写入，核对扩展错误码。
3. **长读与 checkpoint**：明确关闭自动 checkpoint 或固定阈值，制造可观测写入，检查读者释放前后 checkpoint 进度；不把某一次文件大小当通用结论。
4. **在线备份一致性**：使用固定机制制造尚未 checkpoint 的提交，在受控时点对比主文件副本与受支持备份方式，检查数据和完整性。结论只限已验证条件。

实验使用 barrier/握手，不以长 sleep 推测进程时序；显式关闭连接和清理临时目录。正常结果和预期失败均有断言。实验输出可用于核验金标准，但被测报告若没有实际运行实验，不得将它计为“被测系统实测”。

## 6. 独立评分流程

顺序：校验产物 → 锁定 revision → 提取主报告事实 → 匹配要点 → 核验事实及引用 → 裁决冲突 → 聚合分数 → 关联诊断。

### 6.1 主报告是交付质量评分对象

- 从最终主报告的摘要、正文、表格和结论提取原子事实，包含没有引用的事实；不只读取已保存 ClaimRecord。
- 用 reportPlan/ClaimRecord 对齐稳定 ID 和引用，但不复用 runtime 的 supported 标签作为正确答案。
- 附件中有、正文未回答的内容不能增加正文覆盖；单独统计“证据已到达，但报告未交付”。
- 将来源自述、事实、假设、建议及推理分别识别；核验建议的前提和推导。
- 对同一事实去重；一个句子可支持多个评分点，但每点必须独立满足，重复表达不重复加分。

### 6.2 指标及分母

| 指标 | 定义 |
|---|---|
| 正确覆盖率 | 每个预设点计正确 1、部分 0.5、错误/遗漏/无答案 0，按冻结权重聚合；只有预定义的非关键子条件允许部分分，缺决定性条件计 0 |
| 证据支持覆盖率 | 以全部预设点为分母，仅正确且在报告中有充分有效证据支持的部分计分 |
| 原文明示交付完成率 | 仅明确版，检查预先标明的原文要求；不与探索覆盖混淆 |
| 全文事实准确率 | 主报告全部去重原子事实为分母；正确、部分、错误、不可核验分别列数，并单列已核验比例，不隐藏不可核验事实 |
| 引用支持率 | 按事实—引用关联逐项检查证据是否支持完整结论；来源相关、锚点存在并不等于支持；另列未引用事实比例和充分支持事实比例 |
| 冲突裁决率 | 预设冲突案例为分母；核对对象、时间、版本、真实冲突、采信与排除理由。没提冲突不能自动判正确 |
| 重大错误数 | 与预先冻结的重大误解逐一匹配，不能被其他项高分抵消 |
| 有效产出成本 | 已确认探索/报告/内部校验 token、调用次数、耗时分别列出；按正确且有支持的要点数计算成本，未知量单列 |

空报告覆盖率为 0；无事实或无引用时相应比例为 null/N/A，不能得到 100%。当金标准或裁判自身无法裁决时标 `pending_review` 并展示评分区间，不把它当系统回答“不知道”混算。裁判待复核项未完成前不产生最终合格标签。

固定快照支持离线事实与引用复核。替代来源不在金标准快照中时，先判断其适用范围并完成独立核验；没有核验完记待复核，不能因 URL 不在白名单就判错。

### 6.3 自动裁判与人工裁决

- 规则负责 schema、ID、版本、hash、引用解析和确定性聚合。
- LLM 负责语义候选匹配、条件完整性及证据蕴含判断，输出结构化标签、报告区间和证据区间；不保存思维链。
- 每个 criterionId 和事实 ID 必须恰好一个判断；重复、额外、缺失、无效区间均为评测错误，不默认补 supported。
- 裁判输入隐藏被测 commit、版本标签、运行顺序、runtime 评价和预算，降低身份偏差。
- 裁判固定 provider/model/prompt/schema 版本并独立记账；尽可能使用不同于被测生成模型的裁判，若没有则明确记录同模型局限，不能以此阻断规则和人工评估。
- 默认不在评分过程中临时自由联网改变答案；新证据复核是显式、可记录的证据包更新步骤。
- 首轮人工核对全部重大项、冲突项、自动判错项、待裁决项，并抽检至少 20% 的自动判对项。全表未经人工复核时清楚标明复核覆盖率。

## 7. 先校准评测器，再评系统

建立至少 20 个小型合成报告/证据 fixture，覆盖：完整正确、少答但句句正确、关键限定条件缺失、错误版本、数字/否定词翻转、引用错绑、snippet 冒充正文、正证误标反证、已解决与未解决冲突、正文遗漏而附件存在、无引用额外事实、重复刷分、空报告、无效 manifest、重复裁判 ID、未知用量、恢复重复结算等。

其中一组专门断言：从正确报告删掉一半关键内容后，引用准确率即使不变，覆盖率也必须降低；再加入无依据的事实，全文准确率或未核验比例必须恶化。

工程验收：确定性 fixture 全部通过；关键反例不得误判为合格。语义裁判在人工标注的校准集上报告逐标签混淆矩阵、误判和漏判，不只给总体一致率。暂定总体标签一致率至少 90%、重大错误误放行 0；未达到则保留人工裁决通道并标为实验性，不能用不可靠自动分数排名。

校准 fixture 应有独立保留样本；不能反复按同一批样本调整 prompt 后用其成绩宣称泛化。

## 8. 运行编排与预算

### 8.1 首轮矩阵

| 主题 | 明确版 | 开放版 | 总数 |
|---|---:|---:|---:|
| Redis | 2 | 2 | 4 |
| SQLite | 2 | 2 | 4 |
| 合计 | 4 | 4 | 8 |

固定 executionVersion、claimReviewVersion、源码 commit、lockfile hash、模型和参数、js-eyes 版本及 Google skill hash、语言、地区、搜索页数、并发、读取后端、rerank/embedding 配置和预算。秘密值不写入 manifest，配置 hash 只覆盖非秘密字段。

Google skill 的实际名称从当前安装环境探测并冻结，不写死未经确认的名称。每轮用 `npm exec --package=. -- jdr research ...` 发起，使用参数数组 spawn，不拼接 shell 字符串。

默认一次一个真实 run，避免共享浏览器和站点限流引入额外变量；按固定 seed 打乱题目/问法顺序，重复运行分散到不同轮次。每个 run 使用独立会话，不复用上一 run 的研究记忆、答案或归档；浏览器登录状态和搜索地区保持一致并记录，不为测试清空用户个人浏览器。

### 8.2 配置与花费边界

- 搜索：js-eyes Google；策略 exploratory。
- 探索下限 600000、上限 1000000，不变更默认合同。
- 正式矩阵拟设置每次研究总保险丝 1300000 tokens，探索、报告、内部校验全部在其范围内；达到上限如实计失败或不完整，不追加额度美化结果。
- 8 次探索的目标下限合计 4800000、探索上限合计 8000000；总保险丝合计 10400000，不含外部评测裁判。它们是配置边界，不是保证实际使用量或精确账单。
- 未知调用保留预约；报告和评估不补探索下限。提前安全停止仍保存并评分，不空转，不重跑至出现满意结果。
- 外部裁判每份报告拟设 100000 tokens 上限、全批次 800000；超限标评测未完成，之后可只恢复评测。额外人工校准与证据建设成本独立记录。
- 搜索/读取次数帽沿用探索默认，并在 manifest 明确；设置每 run 120 分钟墙钟安全上限，超时发送 CLI SIGINT 并验证停止。此时限是本轮实验条件，未来改变必须新建 protocolVersion。
- 不执行 `config set`；单次覆盖使用 CLI flags。使用 `--no-save` 避免新增应用历史记录；当前完成管线在没有 record id 时也不会归档到 intel。仍会读取既有设置，不宣称完全不访问 SQLite。
- 运行产物落在已忽略的 `work_dir/quality-benchmark/<campaignId>/`；评测包在 `data/research-eval/`。这两处均不提交或直接展示。

运行前生成可检查的 dry-run manifest，包括 8 个 query、实际解析配置、命令参数、预算和输出路径；dry-run 不调用搜索/LLM，不展示密钥。

### 8.3 失败、恢复与比较资格

状态至少区分 queued、running、research_complete、research_failed、cancelled、artifact_invalid、evaluation_pending、evaluated。研究完成、floorStatus、评测完成、内容质量分别记录。

- 探活失败记环境失败，暂停发起后续 run，防止连续 8 次重复失败。
- 研究失败保留在计划的 8 个 run 中，交付成功率以全部预定 run 为分母；有有效完整报告的内容分单列，不能用幸存样本成绩代替整批结果。
- 恢复同一 run 继续用原 campaignRunId 和 session，累计全部执行段；只恢复报告/提交时不算新的独立重复样本。
- 只评测已完成结果不会再次搜索或生成报告；恢复评测不会改写研究结果。
- 不自动使用 continue-explore 为某个差结果补课；新增探索属于新实验段，不能替换基线。
- 程序缺陷导致新增重跑时保留原失败样本、原因和关联 ID，并单列重跑，不删除原结果。

## 9. 失败阶段定位

对每个未得满分的要点生成证据链：

`criterion → 搜索候选 → 正文版本 → passage → inspection/claim → slot binding → 正文位置`

| 观察 | 诊断 |
|---|---|
| 未观察到可用来源候选 | `discovery_gap`，只说明本次记录没发现，不宣称网上不存在 |
| 有候选但没有相应成功正文读取 | `read_gap`，区分未调度、网络失败、过滤和正文截断 |
| 正文含必要事实但未形成有效片段/主张 | `extraction_gap` |
| 有相关片段但对象、版本、支持或反证判断错误 | `adjudication_error` |
| 判断正确但没有绑定到应答问题 | `binding_gap` |
| 有有效绑定但最终报告缺失或表达改变条件 | `report_omission` / `render_semantic_error` |
| 缺少可验证事件或中间状态 | `unattributable`，不能猜归因 |

允许一个要点包含多个失败标签，给出最早有证据的失效阶段及置信程度。候选匹配接受等价来源，不要求系统必须命中金标准 URL。完整证据包仅用于事后判断正文中是否有答案，不给研究阶段补正文。

在已有检查点上离线计算“首次发现来源、首次读到有效事实、首次正确判断、最终交付”的时点与累计确认 token。它是证据获取曲线，不冒称中途报告质量曲线。内部字段若不足，先标缺测；只有确定无法定位的重要问题才增加通用、脱敏观测字段。

## 10. 实时基线与可重复回归分开

真实 Google 矩阵测试端到端表现，但搜索结果和网页会变化。冻结题目和标准答案不能使 live 网络确定化，必须记录实际抓取时间和正文版本。

保留三类结果并分别标记：

1. **live_google**：完整搜索、读取、判断和写报告，作为首轮 8 次主评测。
2. **artifact_rescore**：相同冻结报告与证据重新评分，只比较评测器差异。
3. **component_fixture**：固定输入证据测试提取、反证、绑定、报告表达等具体模块，只定位修复，不作为端到端得分。

现有 replay 是单次已录制调用的重放，不能宣称能支持新 planner 任意查询的完整离线调研。若以后需要端到端离线搜索，必须另建冻结语料、确定性索引与搜索接口，并作为独立协议评测；首轮不扩展到这一步。

## 11. 代码与产物组织

以下是拟新增路径，实施前不存在的文件不要当作已有功能：

```text
scripts/benchmark-quality.mjs                 # validate / plan / run / score / compare
scripts/benchmark/quality/
  schema.mjs                                 # case、rubric、campaign、judgment 合同
  load-case.mjs                              # 运行定义与评测包分开加载
  campaign.mjs                               # CLI 子进程、状态、预算、恢复
  load-result.mjs                            # 锁定 revision、复用 manifest/evidence API
  report-facts.mjs                           # 全文原子事实及位置，不信任 runtime verdict
  judge.mjs                                  # 结构化语义评测、缓存、裁判独立用量
  score.mjs                                  # 确定性指标与缺失/待复核处理
  diagnose.mjs                               # 事后失败阶段定位
  compare.mjs                                # 协议一致性和逐项差异
  format.mjs                                 # JSON、Markdown 与人工复核表
benchmarks/research-quality/v1/
  suite.json                                 # 两题四种输入及默认运行协议
  cases/*.json                               # 公开 query 和适用范围
  evidence-sources.json                      # 公共 URL、版本、hash 等安全索引
  README.md                                  # 核验与操作说明
tests/benchmark-quality-*.test.mjs
tests/fixtures/research-quality/              # 合成数据，不放真实运行产物
scripts/benchmark/quality/oracles/sqlite/     # 固定版本行为实验
```

本地评测包：`data/research-eval/<rubricVersion>/`，保存 rubrics、正文快照、人工裁决和 oracle 结果。运行目录保存 campaign manifest、各 run 引用、score.json、diagnostics.json、review-items.json、comparison.md。最终对外只提供脱敏汇总及代码/文档，不直接展示运行产物。

新评分字段使用独立 `benchmarkSchemaVersion / rubricVersion / judgeVersion / protocolVersion`。不复用容易混淆的 quality.metricsVersion，不覆盖保存结果的 quality_json 或 reportPlan。旧 benchmark 命令及输出保持兼容。

接口示意，实施时落实 help 与参数校验：

```bash
npm run benchmark:quality -- validate --suite benchmarks/research-quality/v1/suite.json
npm run benchmark:quality -- plan --suite benchmarks/research-quality/v1/suite.json
npm run benchmark:quality -- run --campaign <campaign-manifest>
npm run benchmark:quality -- score --campaign <campaign-manifest> --gold-dir <gold-dir>
npm run benchmark:quality -- compare --baseline <campaign-a> --candidate <campaign-b>
```

`run` 只接受公开运行 manifest，不接受 gold-dir；`score` 才加载标准答案。所有命令默认本地输出，不上传、不发通知、不发布。

## 12. 验收与改进判定

### 12.1 评测设施验收

- 两题全部评分点有核验记录、明确版本/条件和可解析证据锚点。
- 参数与金标准隔离测试通过，原始 query 不被隐藏要点扩写。
- 相同报告、rubric 和已保存裁判判断重复聚合，结果完全相同。
- manifest 损坏、revision 错配、缺正文、非法判断结构均不能产生有效分数。
- SQLite 实验在固定环境可重复；fixture 覆盖所有重大误放行情形。
- 评测自身不会改写研究产物或向研究预算重复结算；凭据和原始页面不进入提交。
- 相关测试、`npm test`、`npm run lint`、`npm run build` 通过。测试工具和 fixture 为必要验证，真实 Google 不加入默认 CI。

### 12.2 第一版报告质量目标

以下是实施前预设的工程目标，不是现有系统已达到的结论：

- 已交付结果产物完整性通过；重大事实错误为 0。
- 明确版正确覆盖率至少 90%，证据支持覆盖率至少 85%。
- 开放版核心正确覆盖率至少 80%，核心证据支持覆盖率至少 75%；附加发现单列。
- 全文严格事实准确率至少 95%，全文事实核验覆盖至少 95%，不得隐藏未核验事实。
- 引用支持率至少 95%，关键结论均有充分证据；重大冲突案例全部正确裁决。
- 无待复核重大项；每个未完成要点可定位或明确标缺测。
- `floorStatus` 和总交付成功率独立报告，不用内容分抵消执行失败。

基线不达标仍算评测计划成功执行；其目的正是发现缺陷。基线结果差不得阻止出具完整诊断，也不能先修答案再称之为基线。

### 12.3 如何认定修改有效

先冻结基线 commit 和评分协议，再实现单个通用缺陷修复。用 component_fixture 确认因果机制后，使用相同矩阵建立候选批次；有条件时交错运行基线与候选，减少网页时间漂移。

每个 topic × prompt 的原始两次结果全部展示，报告均值、范围、重大错误、失败率和成本差异；两次重复仅用于发现波动，不声称统计显著性。没有可配对随机性时明确称为同条件组间比较。

暂定改进判据：目标失败项在两个重复中均改善；其他核心项不退化；总覆盖、重大错误和交付成功率不因修复恶化。若预算明显上涨，展示质量/成本取舍，不以更多调用直接宣称算法更好。指标不一致时增加预先定义的复测批次，而不是挑选最好结果。

下一轮再加入 Python 3.13.0 自由线程题作为新主题迁移验证；其答案在调试 Redis/SQLite 时不参与反馈。

## 13. 分阶段实施与提交顺序

| 阶段 | 工作与交付 | 进入下一阶段的条件 |
|---|---|---|
| P0：冻结范围 | 题目、版本、运行协议、指标 schema、预算 dry-run；记录基线 commit | 四个 query 和评分边界没有歧义 |
| P1：建立金标准 | 两题约 40 个评分点、版本化原文、冲突裁决、SQLite 实验、核验记录 | 核心事实均可独立核验，无悬而未决的标准答案 |
| P2：实现独立评分 | 全文事实提取、证据核验、要点匹配、裁判合同、确定性聚合、复核表 | 校准 fixture 与重大反例通过，语义裁判局限明确 |
| P3：实现运行与诊断 | CLI 编排、manifest 锁定、预算/恢复、阶段归因、对比输出 | mock CLI 测试通过，无凭据泄露或运行产物污染 |
| P4：建立真实基线 | 固定配置执行 8 次 live Google；先完成首个 run 的管线完整性检查，再继续其余 7 次 | 首次发现的是评测设施问题则先修设施并保留记录；研究质量差本身不暂停矩阵 |
| P5：复核与交付 | 人工核验、8 次完整分数、逐要点失败链、成本和波动、修复优先级 | 每个修复建议有失败样本与验证方法，无按主题硬编码方案 |

建议提交分为：题库/schema 与 oracle；独立评分与校准；campaign/诊断/比较；使用文档与脱敏基线结论。真实数据与金标准正文只保留本地。

最终修复清单每项包含：问题机制、影响要点和 run 数、失败证据、涉及模块、拟修复原则、回归 fixture、预期改善及风险。优先修复重大误判和证据已读却丢失的问题，再优化无效搜索与花费。
