# 调研系统优化第一轮：实施与验证计划

日期：2026-09-10。状态：待实施。本次仅编写计划，未修改程序、运行测试、调用裁判或启动调研。

## 1. 本轮要回答什么

本轮实施后，应当能用保存的证据回答三个问题：

1. 搜索服务失效或任务中断后，系统能否停止无效消耗，并按原配置、原账本继续？
2. 对已经读取的同一批正文，系统能否交付更多经过验证的答案，同时避免反复整体审查？
3. 评分能否区分答案遗漏、事实错误、证据不足、运行故障和评测未完成？

交付包括：通用代码修复、故障回归用例、版本化评测、已有报告重评、固定正文重建实验、真实 Google 候选批次及结论。完成代码、完成实验、证明质量改善分别记账；不能用“运行结束”代替“优化有效”。

### 给使用者看的执行顺序

| 步骤 | 做什么 | 如何知道做好了 |
|---|---|---|
| P0 冻结样本 | 保存当前代码身份、原始报告版本、故障样本和验收标准 | 后续比较不会换题、换答案或丢弃失败样本 |
| P1 修搜索故障处理 | 服务不可用时暂停依赖动作，正确区分无结果与服务故障 | 故障后无新增规划消耗，可从原进度恢复 |
| P2 修续跑和任务状态 | 冻结执行配置、准确校验预算、恢复失效运行状态 | 续跑保留 16,000 报告上限，已保存调用不重复执行或结算 |
| P3 修评测 | 陈述分类、规则评分、逐项保存、重新校准 | 固定反例全部通过，旧报告得到可解释的分数或明确待评项 |
| P4 修答案组织 | 用户要求独立保存，每项绑定多个具体结论 | 已验证部分能够进入报告，未解决部分仍明确标缺口 |
| P5 修验证调度 | 新证据只影响相关结论，探索与报告共用验证状态 | 无变化不重复审查，新增反证仍能使结论降级 |
| P6 分层验证 | 固定正文重建，再完成同条件真实调研 | 给出运行、内容质量、成本三个维度的结果 |

默认顺序实施。P3 对原报告重评完成并冻结后，才开始 P4/P5 的质量调优。每阶段有独立提交边界，方便定位回归。

## 2. 已知事实和本轮假设

以下来自上一批中间产物和对应代码检查；详细原始产物仍只保留本地。

| 观测 | 可以确定的机制 | 本轮验证的修复假设 |
|---|---|---|
| 最后三次共 356 次失败搜索、零正文读取；130 次查询规划消耗约 440,988 tokens | 搜索调用持续失败后，调度器仍继续规划；启动 TCP 连通检查不能证明搜索可用 | 服务健康状态进入调度和批次控制后，可切断这类无效消耗 |
| Redis 续跑总确认用量 641,307，未达到 1,300,000，却报总预算耗尽 | 报告上限在账本中为 16,000，续跑报告配置却回到默认 0 | 单一有效执行配置和入口一致性校验能消除错误拒绝 |
| 两个明确版 query 未提取独立 inputTasks，问题落在一个大槽位 | 原文枚举识别较窄，一个槽位又通常对应一条较大主张 | 保留独立原文交付项、拆分结论后，可减少整项缺口压住有效部分的情况 |
| SQLite 明确版第一次 129 次 gap_support，约 929,318 tokens，占探索用量约 96% | 问题与正文广泛关联，并反复整体判断答案；已有缓存，但请求并不完全相同 | 按结论依赖和新增证据调度，可减少无变化复核；不能先断言这些调用全部无效 |
| 一个零覆盖报告被抽出 25 条计划、状态、限制等陈述，全部判不可验证 | 技术知识评测与执行状态审计混在一起 | 分类验证后，零答案仍为零覆盖，技术准确率不再被无关陈述扭曲 |
| 多份评分因非法 partial、缺少冲突判断、正确但无证据而失败 | 模型承担了确定性评分规则，同时单项错误影响整批进度 | 程序执行规则、逐项检查点和有界重试能提升评测完成度 |

仍未确定：JS Eyes WebSocket 关闭的底层原因、ENOSPC 对应的具体存储瓶颈、内部 supported 标签是否都经独立裁判认可。本轮不能把这些推测写成已证实根因。

上一批共 8 次尝试、7 份报告、2 份机器评分草案；裁判校准 85%，未达 90%。最后三次有服务故障，另一次存在续跑配置错误。因此，旧批次用于保留故障分母和分析机制，不能作为无污染的两次重复质量基线。

## 3. 范围和固定约束

### 本轮包含

- JS Eyes / 通用搜索错误合同、搜索健康状态、探索调度、CLI 和批次暂停恢复。
- 有效执行配置快照、预算配置校验、会话/批次锁、失败后的状态核对。
- 评测陈述类型、证据核验输入、确定性评分、逐项恢复、校准与比较口径。
- 请求交付项、原子主张、多对多绑定、部分答案交付、增量复核及统一完成判断。
- focused 的共享请求/主张/报告路径兼容测试；本轮真实效果验证只跑 exploratory。

### 本轮不包含

- 换模型、提高预算、切换搜索提供方、加入新主题或改写 Redis/SQLite 标准答案以适配输出。
- 新的通用工作流框架、多智能体架构、向量数据库、Wiki/Intel 管线重写或 UI 大改。
- 自动启动/重启 JS Eyes、改变浏览器登录或信任设置，以及无限后台重试。
- 把所有旧会话迁移为新算法、改写旧完成报告，或重跑 8 次旧基线作为额外对照组。

### 必须保持

1. 原始 query 保持原样；planningContext 仍只有 questions / identityHints / readingHints，不能成为人类硬要求。
2. 探索下限 600,000，上限 1,000,000；正式单 run 总上限 1,300,000，报告输出上限 16,000。未知用量保留预约，不当成零，也不补探索下限。
3. 来源正文、UTF-16 锚点、主张支持/反证、推导前提及引用完整性继续严格验证。未绑定观察不能自动进入报告。
4. `[n.m]` 只经 citations 注册表解析；API、评测和恢复都锁定 resultRevision / manifest，损坏不回退 findings 正文。
5. 主张及表达校验的 ID 必须完整、唯一；结构错误不能默认通过。
6. 旧完成结果继续交付原 revision；只有显式继续探索才能在已终止探索后增加执行段。
7. 搜索词仍仅来自原始 query 或 Planner；不新增按主题拼词、域名表或静态搜索路由。
8. 默认本地执行，实验只用一次性覆盖配置。原始正文、调用内容、金标准正文、凭据及本地运行产物不进入提交。

## 4. P0：冻结可比较的输入和故障样本

### 工作

- 记录当前 HEAD、实际 runtime 文件 hash、lockfile hash、评测器 hash、Google skill 身份和有效公开配置。当前存在未提交的评测实现，不能仅用 HEAD 描述实际基线，也不能覆盖这些改动。
- 通过 readArtifactManifest / readArtifactEvidence 锁定 7 份旧报告的 revision、reportHash、manifestHash、证据包 hash；没有报告的失败 run 继续保留在 8 次尝试分母内。
- 冻结两个主题、四种 query、已有事实金标准和版本范围。事实答案保持现有 quality-gold-v1.1；评分协议独立升级，不能混用不同裁判版本的百分比。
- 保存针对以下机制的最小合成 fixture：服务断连、非零退出但缺少结构化错误、有效空 SERP、续跑丢报告配置、磁盘写失败、孤儿子进程、复合答案部分支持、扩展方向冒充要求、重复复核、反证到达、评分结构错误。
- 真实产物的索引和派生诊断放本地忽略目录；仓库 fixture 用自写短文本和模拟响应，不复制整页正文、原始日志或完整报告。
- 建立统一验证清单：每项记录输入身份、期望行为、实际结果、失败阶段、调用数、确认/未知用量、产物完整性与复核状态。

### 验收

- 现有正常和失败结果都能只读定位；损坏/缺失项明确标记，不能从其他版本借资料。
- 新测试在当前实现上能复现对应缺陷；已有正确行为列为必须保持的反例。
- 冻结质量指标、预算和样本选择规则后再改 runtime。发现标准答案有问题时单独版本化并重评所有相关样本。

## 5. P1：搜索故障进入执行控制

### 5.1 错误合同

在现有 SearchProviderError / SearchMeta 上增加明确的错误作用范围和执行观测，避免另建一套搜索接口：

- provider / endpoint / skill 的身份、结构化 code、retryable、retryAfterMs、失败发生阶段。
- 区分服务不可用、授权/信任失败、限流、调用超时、未知调用级错误与正常空结果。
- 单个网页读取失败继续属于 source_read；一个 skill 失败不能直接封锁仍可用的其他 skill。
- 仅使用 provider JSON、退出码、信号、超时等可核验观测。不要靠匹配中文日志推导“限流”或认定服务器故障；无法细分时保留 unknown_call_failure。

### 5.2 探活和熔断

- TCP 成功只表示端口可达。doctor 能提供结构化能力时按实际 schema 校验，不只检查退出码。
- 将首次合法业务搜索作为端到端检查：先建立运行记录和预算，再使用原始 query 或恢复时待执行的合法 query，走正式 adapter、预算、回执和结果准入，成功结果复用。不能另造静态探测搜索词，也不能让探测成为不计数的隐形搜索。
- 初次业务搜索失败时，在 Planner 之前返回明确前置失败。成功空 SERP 证明搜索调用完成，但不提供研究证据，也不宣称已证明所有搜索能力正常。
- 运行中按错误作用范围维护 healthy / suspect / open / half_open。明确不可恢复的授权或配置错误立即中断；默认连续 3 次调用级失败触发熔断。正常空 SERP 不计失败。
- 保留现有 provider 结构化重试合同：未知错误不隐式重试；retryable 错误有限重试并尊重 retryAfterMs。健康模块不再叠加一层无限重试。
- 熔断后停止受影响的新搜索及依赖这些搜索的 Planner 调用；保存检查点和回执后退出，不继续生成“搜索方向耗尽”的最终报告。只有受影响通道失效时，不牵连其他健康通道。
- 本轮不增加数据库顶层 paused 状态：CLI/历史记录为带明确错误码的 failed，运行检查点记录可恢复的 interruption，campaign 记录 environment_paused。研究的 stopReason 不伪造 evidence_sufficient / safety_cap；已有终止原因也不改写。
- 恢复时先做一次有界检查，再继续同一状态和账本。再次失败即保留暂停状态，不自动循环唤醒。

### 5.3 验收

- 假 TCP 服务能接连接但不能执行搜索：0 次 Planner，0 次正文读取，明确前置失败。
- 顺序 Google 搜索在成功后持续失败：最多达到配置的 3 次失败阈值；熔断后的新增搜索与 Planner 次数均为 0。若有 provider 内部重试，实际调用数另列；并发测试需计入触发时已在途请求。
- 正常空结果不会被标成服务故障；单网页 403 不熔断搜索服务；单 skill 失败不停止健康 skill。
- 结构化限流不计为“查询想不出来”；取消能打断等待并保留准确回执。
- campaign 在已有 session 的服务故障下也暂停，其余未启动 run 保持 queued。

主要入口：src/search-preflight.mjs、src/search-providers/js-eyes/*、packages/js-deepresearch-engine/src/search/search-provider-error.mjs、engine search-executor.mjs / exploratory-search.mjs / exploratory-action-loop.mjs / resume-plan.mjs、scripts/benchmark/quality/campaign.mjs。

## 6. P2：统一配置恢复、预算校验和运行状态

### 6.1 有效执行配置

- 在完成配置归一化后、首次外部调用前，生成带 schemaVersion / configHash 的 RunExecutionConfig。采用显式可恢复字段清单，而非直接持久化整个 settings 对象。
- 保存模型身份、策略、搜索/阅读语义、预算、报告设置、相关验证版本等非秘密执行参数。凭据、含秘密的连接信息单独从当前环境绑定，不写入快照。
- CLI、Web JobRunner 和 engine 恢复入口共用同一个 resolver。provider 创建、探活、BudgetManager、报告设置均使用 resolver 的同一结果。
- 新建任务仍按 CLI > 环境 > 持久设置 > 默认值解析；同一执行段恢复以冻结配置为准。当前环境中的模型、搜索语义或预算变化不能静默替换快照。
- 已有 continue-explore / extra steps、reads、searches 等显式变更追加执行段和变更依据。不能重置已花用量或未知预约；本轮不开放任意字段的静默覆盖。
- 旧未完成会话按确定性来源恢复：已有检查点/预算中的报告上限、已记录的有效设置、可验证的本次批次协议；记录字段来源。若值冲突或必要字段缺失，外部调用前报缺失/冲突字段，不猜测默认值。Redis 样本应从已保存 16,000 上限恢复。
- campaign 对比实际解析后的 configHash，而非根据假想的初始 flags 计算身份。普通 resume 不应依赖再次手工复制一整串 flags 才能保持正确。

### 6.2 预算错误分流

- 有总保险丝但报告输出无有限上限：报 INVALID_REPORT_BUDGET_CONFIGURATION。
- 配置有效但剩余额度不足：才报真实 budget_exhausted，并指出阻止的请求类别。
- 存在未知调用：显示确认用量、未知预约和可用额度；不把未知当零，不重复结算已保存响应。
- 边界异常不能清空已有研究状态。尤其覆盖恢复循环中 BudgetExceededError 的 findings 兜底路径，确保能用最后有效状态收尾；这项属于风险回归，不冒充已观测 Redis 根因。

### 6.3 生命周期

- 复用 src/session-lock.mjs 的 SQLite OS 锁方式管理 campaign writer；保留每个研究 session 的独立锁。锁文件存在不等于仍在运行，不删除正在使用的锁。
- 记录 attemptId、子进程身份、开始/结束和最后检查点；心跳辅助显示，锁与实际进程状态负责排他。PID 单独不足以证明原进程仍活着。
- 在落盘 onStarted 或后续回调失败时，清理已启动的本任务子进程并释放资源；不得留下继续烧预算的孤儿进程。只处理能确认属于该 attempt 的进程。
- 重启后核对 checkpoint、最终结果、attempt 和进程状态：已经完成的只交付，失去进程的 running 标 interrupted，状态不足时标 unknown 并阻止重复派发。
- ENOSPC 明确归为存储失败，停止后续外部调用。错误记录只含安全错误码、路径角色和存储诊断；盘满时不保证还能写 failure.json，以最后有效边界恢复，不假称落盘成功，不自动删除用户数据。
- 每个 run 的总用量和主动运行墙钟在多次 attempt 间累计。服务暂停等待时间单列，不靠重启获得新的预算或完整 120 分钟额度。

### 6.4 验收

- 首次有 16,000 报告上限，恢复时当前设置为 0：实际报告请求仍为 16,000，预算配置 hash 一致。
- 重现 641,307 / 1,300,000 的已保存状态：不再因为配置丢失误报额度耗尽；模拟真正不足时仍拒绝调用。
- 已响应未结算、未知响应、报告前中断、探索中断、最终结果已完成五种边界分别验证不重付、不丢证据、不擅自重搜。
- 双 writer 互斥；进程死亡后锁自然释放；状态回调写失败不会留下运行子进程；ENOSPC 后停止调度并能从有效检查点恢复。
- CLI、Web 共享配置 resolver；report-only resume 的 search 次数为 0，completed-result resume 的搜索和 LLM 次数均为 0。

主要入口：src/cli-research-run.mjs、src/jobs/job-runner.mjs、src/session-lock.mjs、engine research-runner.mjs / resume-plan.mjs / run-recorder.mjs / report-settings.mjs / report-preparation.mjs / budget-manager.mjs、campaign.mjs。

## 7. P3：让评测可信、可完成、可恢复

### 7.1 陈述分类和分母

从主报告完整提取陈述并保留位置、出现次数和引用；不只读取 runtime ClaimRecord，也不采用 runtime supported 标签作为真值。

| 类型 | 验证依据 | 指标处理 |
|---|---|---|
| 技术事实、来源自述 | 冻结金标准、该报告引用的真实正文、归属和版本条件 | 技术事实准确率、核验覆盖、引用支持 |
| 推导、建议 | 技术前提、必要条件及推导是否超出证据 | 前提中的技术断言正常计入事实分母；建议有效性单列 |
| 计划、调查范围 | 原始 query 和计划陈述本身 | 不增加技术答案覆盖 |
| 运行状态 | 锁定的最小运行事实，如 floorStatus、停止原因 | 执行陈述准确性单列 |
| 证据限制 | 实际已读/已验证范围 | 区分“未验证到”和“公开资料不存在”；后者仍是需取证的事实断言 |

- 技术准确率分母包含全部技术断言及技术前提，未引用和不可验证的断言不能被排除。待评项保留范围和数量，不给最终通过。
- 无技术断言时技术准确率为 N/A；答案覆盖率仍按全部固定要点计算，零答案为 0，不能通过质量门槛。
- 类型不确定则 pending_review，不允许通过改写成“建议”“限制”或标题逃避技术断言检查。
- 每个正文块都要有提取决定；事实遗漏、条件被拆丢、表格引用串行错绑纳入回归。

### 7.2 模型给证据判断，程序算分

- 输入使用程序分配的稳定 factId / criterionId / evidenceId，并明确各 ID 的类型。
- 模型返回：匹配的主报告事实、支持与反证 ID、决定性条件满足/缺失情况、冲突是否得到解释。程序基于冻结规则计算 correct / partial / incorrect / missing 和分值。
- 没有预定义部分得分的项目不向模型提供自由 partial 决策；没有 conflictCase 的项目由程序写 not_applicable。
- “事实为真”仍必须有可核验的正文依据；引用支持单独判断。不能因为事实碰巧正确就给无效引用加分，也不能只因未引用就判事实错误。
- 上下文先按相关证据候选组织，去重同一片段；候选选择不是证据验证。缺少决定性上下文时扩充一次有界上下文或标待评，不用模型记忆补答案。
- 固定规则版本和字段转换 hash；若需改变事实金标准或部分分规则，升级对应版本并对所有相关旧/新报告重评。

### 7.3 保存和重试

- 增加 evaluationRevision。旧评测保留，新版本评分写入独立目录，不覆盖旧 score，也不改研究 resultRevision。
- 保存提取块、事实判断、要点判断和聚合阶段检查点。缓存身份包含报告/证据/规则/裁判/校准及输入子集 hash。
- 外层 ID 缺失、重复、额外仍为结构错误，不静默修正成有效判断。外层有效时，可保存独立通过校验的条目，仅对失败条目做一次修复重试；已有阶段的有效结果不因后续失败丢弃。
- 预算不足时缩小未发出的批次和上下文；保留安全预约规则。不能直接放宽估算或把未知请求改成零。响应先落盘、用量仅结算一次的合同保持。
- 待评项输出 coverage 下界/上界及 pending 数量，不把待评伪装成全部错误，也不从分母删除。
- 同一输入和保存判断重复聚合必须完全一致；模型服务与研究运行串行使用，避免共用本地模型时资源竞争。

### 7.4 校准与已有报告重评

- 保留原校准集作为开发集，补充至少 20 条固定保留用例，总计至少 40 条；开发/保留集身份在调优前冻结。包含状态陈述、限制与不存在、一般建议、决定性条件、版本冲突、无引用真命题、正确但错引、结构损坏、事实遗漏。
- 所有确定性结构/安全反例必须通过；固定保留集语义一致率至少 90%，已知重大错误误放行为 0。不得反复修改保留集标签适应裁判；查看保留集后继续调优则记录其已成为开发数据。
- 只有校准达标才进行后续正式内容比较。校准不达标仍输出诊断和复核清单，暂不进入昂贵真实矩阵。
- 使用新评测版本重评旧 7 份报告，失败 run 不造报告、不打内容零分替代缺测。100,000 tokens / 报告，预算覆盖该版本全部评分阶段及重试。
- 所有重大项、冲突项、类型有争议项和修改前后结论翻转项列入复核；另抽查至少 20% 的其余事实。没有真实人工复核时明确为机器草案，不能宣称人工确认；人工缺席不阻止代码和确定性测试交付。

主要入口：scripts/benchmark/quality/report-facts.mjs、evaluate.mjs、score.mjs、judge.mjs、schema.mjs、calibrate.mjs、compare.mjs、load-result.mjs 和 scripts/benchmark-quality.mjs。

## 8. P4：独立交付项与可验证结论

### 8.1 从原文提取交付项

- 扩展通用的显式指令/枚举识别，支持自然中文并列句、编号、多句要求及英文列表。仅在明确指令范围内拆分，不按每个逗号机械拆实体、版本或条件。
- 保留 basisRanges、共享上下文和限制继承关系。日期、实体、版本、否定和前提不能在拆分后丢失；同一原文范围可以为多项提供共同上下文。
- 结构化 requiredAnswerSlots 继续优先且不可被合并吞掉；已经支持的原文解析行为保留回归。
- 模型只能提出候选拆分，不能凭自己的 required 布尔值提升权限。文本区间存在也不等于语义已确认；不能由受限解析确认的要求保留为 unresolved_request_constraint / 未解析原文义务，阻止虚报完全满足。
- 原文剩余指令不能因提取出部分项目而被 root roll-up 丢弃。开放问题只保留原始问题义务，其余调查方向保持可选。
- 每项 missingFacets 需关联原文义务或验证该结论必须保留的条件；额外量化实验、第三方工具扩展等保持 optional，不独立阻断用户交付。

### 8.2 将槽位答案改成多条主张

复用现有 ClaimRecord / SlotBinding，增加粒度，不引入第二套证据真值库：

- 每条 ClaimRecord 表示一个具体命题，保存实体、版本/时间、conditions、kind、supportRefs、counterRefs、premiseClaimIds 和验证身份。
- 一个 task/facet 可绑定多个 claim；同一 claim 可支持多个 task，但每个绑定都需独立确认其回答关系。禁止用任意 Key Finding 充数。
- slot adequacy 与 claim truth 分开：slot 部分完成时，已支持且有有效回答关系的原子主张可以交付，剩余 facet 继续出现在 limitations。
- 复合句不能只凭其中一半有证据而整体发布。拆成两个独立命题后分别验证；无法可靠拆分则保留不可验证状态。
- 推导的前提是经过验证的事实单元，不再直接把整段原文当成一个巨大前提；来源自述与实际行为继续区分。
- 相关但未绑定的观察仍留在 EvidenceStore；不得为增加报告长度自动发布。optional 调查方向可以贡献独立验证且相关的发现，但不能抵消 required 遗漏。
- 报告正文明确区分已确认结论和未完成项目，引用仍由确定性 renderer 附加；不暴露 taskId 等实现字段。

### 8.3 验收

- 两个现有明确版 query 都能保留各项原文明示要求；用改写后的中英文题、否定句、条件句和开放题证明不是按 Redis/SQLite 硬编码。
- 三项要求只有两项证据充分：输出两项结论及第三项缺口，整体 incomplete；不能空掉两项，也不能 complete。
- 同一段的 A 命题有支持、B 命题无支持：只能发布单独验证的 A，且明确 B 未解决。
- 未验证来源自述、反证、推导前提失败和无锚点内容仍无法发布为已确认结论。
- 原有 supported 但 missingFacets 非空的测试保留“不能冒充完整答案”的断言，并新增可合法交付已验证子命题的断言；不能简单删除旧测试换取通过。

主要入口：research-request.mjs、research-brief.mjs、gap-state.mjs、gap-slot-support.mjs、claim-graph.mjs、canonical-report.mjs、report-contract.mjs、report-plan.mjs 及相关测试。

## 9. P5：按新增证据复核，并统一完成判断

### 9.1 增量依赖

- EvidenceStore 正文版本/片段仍为输入真值；对相关范围提取候选事实，保留提取范围和版本。不能把部分范围已提取误写成全文已检查。
- 缓存分两层：正文范围的候选事实提取；固定主张在给定支持/反证/约束和校验版本下的判断。
- 主张身份由程序生成并保存 revision；实体、命题、版本/条件、证据依赖或验证协议改变时失效。只改变文字排版不会触发证据重查；出现新相关反证必须失效。
- 建立 task/facet → claim → passage/version 依赖。新片段先判断影响哪些义务/结论，再只调度受影响验证，不再默认把所有正文与所有槽位做完整复核。
- 保留有界相关反证检查；检索或排序只是选择检查上下文，不能独立证明主张为真或无反证。范围不够时保留 uncertainty。
- 动作进展记录新增有效主张、已补齐义务、已解决冲突。新增文本、重复 supported 标签或仅改写 answer 不单独算实质进展。

### 9.2 共享校验状态

- 从 canonical-report 中抽出可复用的主张验证服务；探索 readiness 与最终 renderer 使用同一验证快照及版本。
- 候选答案/最终主张验证的用量归类保持原口径，即使调用提前到探索循环内部，也不挪进探索下限。正文检查等探索用量与最终验证用量明确区分，并共同受总保险丝约束。
- 存在 required 绑定失效或 unresolved 输入限制时不能标 evidence_sufficient。
- 在探索还未终止且预算允许时，把验证发现的缺口送回现有有界 repair 调度，每 facet 沿用最多 3 次恢复失败限制；没有新证据不重复送同一修复。
- 最终措辞验证若发现新增命题或丢条件，优先修措辞；不能借报告阶段开启隐形搜索。报告恢复继续 search=0，旧 terminal checkpoint 也不自动重进探索。
- 如果验证暴露的问题在预算内无法解决，输出有效部分和缺口；floorStatus、执行停止原因及内容完成度分别保留。

### 9.3 验收

- 同一正文、同一义务、同一验证版本连续推进多轮：新增语义验证调用为 0。
- 新增一段无关正文：不会使全部已验证结论失效。
- 新增相关反证、改变版本/条件或更新校验协议：依赖项必须重新验证，反证有效时不能继续发布旧结论。
- required 主张被严格校验降级时，仍在探索阶段且有预算则执行有界补证；无预算则 incomplete，不先记录 evidence_sufficient 再掩盖矛盾。
- 持久化、恢复和再次执行同一回执后，验证调用和预算都不重复。
- 有效主张数量仅用于诊断；效率评价以固定外部评分点为单位，避免通过拆出更多小句虚增收益。

## 10. 版本和兼容策略

- executionVersion 保持 2；新增独立 runConfigVersion、requestContractVersion、claimGraphVersion 和 validationProtocolVersion，不把所有变化塞进 executionVersion。
- 修改主张语义后将 claimReviewVersion 从 3 升至 4，更新相关 schema reader/writer、缓存身份、AGENTS 和文档。旧已完成结果不重审；旧未完成报告在新版本下必须重审，不能直接信任旧 supported。
- 新主张图的一个 task 多个绑定会影响 renderer、readiness、指标和导出。全仓检索对 binding.claimId、taskId 唯一性的假设，统一更改；旧 schema 经显式适配读取，不模糊混用。
- 老的 gap.slotSupport.answer 只作为旧复合候选输入，不能迁移时自动变成若干 supported 原子主张。
- 已登记的引用编号保持稳定，新编号追加；主报告实际引用数与历史注册表总数继续分开。
- 评测 schema / judge / scoring protocol 独立升级，旧结果不可覆盖。比较器拒绝把不同规则版本直接算 delta；原报告可经新裁判重评后比较。
- 新字段进入 checkpoints、result manifest、无 work-dir 内联结果及 API 同版本交付测试。保留既有 SQLite/Intel 提交原子性，本轮不重写其管线。
- 回退按明确版本和提交操作，不在校验失败时自动退回较宽松证据路径。候选会话不能直接交给不支持其 schema 的旧代码继续写。

## 11. 验证矩阵和执行门槛

### 11.1 第一层：无网络故障与合同测试

### 11.2 第二层：旧报告重评与固定正文重建

1. P3 校准后重评旧 7 份报告，生成新版本基线；缺测及复核状态保持可见。
2. 选取旧批次第一次重复的四份已交付报告，即两个 topic × 两种问法各一份，不挑最高分。固定其原始 query、已读正文版本与可用范围，禁止提供金标准、评分点、裁判反馈或旧 supported 标签。
3. 用候选引擎执行显式 artifact_rebuild：禁用网络搜索/抓取，只运行请求理解、正文检查、主张验证和报告生成，结果写入新的诊断目录，不能覆盖原会话。
4. artifact_rebuild 不是正式探索 run，不适用“达到 60 万”的完成声明，也不混入 live_google 交付率。其阶段用量完整单列。
5. 同一新裁判重评四份重建报告，逐评分点比较哪些原来已读的证据现在进入正文，检查新增错误、丢失条件和遗漏。

这层能验证“已读证据能否更充分地交付”，不能证明搜索变好或总成本降低。旧完整流程与固定正文重建的输入时序/预算不同，不对二者总 tokens 作算法效率结论。调用重复机制由第一层依赖测试验证，真实成本由第三层观察。

预设改进目标：四份重建报告的证据支持覆盖率中位提升至少 10 个百分点，无新增重大错误，原有正确核心点不退化。它是待验证目标，不是承诺；未达到时记录为该假设未获支持，不事后降低阈值。

### 11.3 第三层：真实 Google 候选批次

- 进入条件：第一层回归全部通过，P3 校准达标，旧报告与重建报告已完成新版本评分，固定正文改进目标达成。任一条件未满足，本轮不启动新的昂贵真实批次，保留当前结论和缺口；不靠追加模型调用或降低门槛强行进入下一层。
- 仍使用 Redis / SQLite × 明确/开放 × 2 次，共 8 个 run；原始 query、版本、模型、skill、语言、每次搜索页数和预算保持冻结。
- 新 candidate campaign 独立保存，记录代码/配置/验证协议身份。先运行一个 Redis 和一个 SQLite 作为链路检查，它们计入这 8 次；余下 6 次按事前固定顺序执行，不能把内容低分的先导样本删除重来。
- 同一时刻只运行一个研究或裁判，避免本地模型资源竞争。单次运行预算跨 attempt 累计，真实断连恢复沿用同一个 run，不制造替换样本。
- 每 run 最多一次基础设施恢复尝试；无法恢复或再次失败则暂停本轮并交付状态。未启动项仍为 queued，不能写成“已完成 8 次”。这不是给查询增加语义重试额度。
- 校准未达标、产物完整性失败、有效配置漂移、服务不可用或存储故障时暂停进入/继续真实矩阵。报告内容差本身不暂停、不挑选样本。
- 保留旧 8 次和新 8 次的全部尝试，分别给交付状态与内容分。旧环境故障样本单列原因，不删除，也不当成模型事实准确率的零分。
- 两次重复仅反映小样本波动，不声称统计显著。旧批次受环境污染，真实前后对比只给方向性证据；若需要因果量化搜索能力或稳定成本收益，另行计划同期基线对照，本轮不追加。

## 13. 最终验收和效果判定

### 实现验收（必须全部满足）

- 第一层列出的故障/合同用例全部通过；npm test、lint、build 通过。
- 服务故障不再触发无界规划；原配置可恢复；运行状态与产物一致；无重复结算和秘密泄露。
- 两个明确 query 及通用改写的交付项正确保留，部分答案交付不放松证据校验。
- 不变输入不产生新验证调用；相关反证、条件和协议变化能正确失效。
- 所有新旧 schema、完整结果恢复、report-only 恢复、focused 共享路径和 API 同版本证据交付通过回归。

### 评测可用性验收

- 固定校准保留集一致率至少 90%，重大错误误放行 0；确定性评分反例全部通过。
- 每份报告均有完整分数或逐项 pending 和预算原因；没有 generic structure error 导致已完成阶段全部丢失。
- 正式比较优先要求 7 份旧报告、4 份重建报告和实际交付的候选报告完成评分；若未完成，只交付区间与缺测，不给最终提升标签。
- 类型分母、校准身份和人工复核状态在结果中明确。没有人工复核仍只称机器评估草案。

### 质量与效率目标（用于判定改进，不用于修改评分规则）

- 固定正文重建达到第 11.2 节的覆盖改进目标。
- 真实运行目标 8/8 正确交付完整产物；交付成功与内容 complete 分开，不用限制说明报告冒充充分回答。
- 沿用既有质量目标：明确版正确覆盖至少 90%、证据覆盖至少 85%；开放版核心正确覆盖至少 80%、核心证据覆盖至少 75%；技术事实准确率、核验覆盖率、引用支持率各至少 95%；重大事实错误 0、重大冲突正确处理、关键项无待复核。
- 展示每个 case 两次的原始值、均值/范围和错误条目，不只给总体均值。
- 成本同时列探索、报告/主张验证、独立评测、未知预约和实际搜索/读取调用；按固定评测点计算每个完整且有证据的要点成本。分母为 0 时 N/A，不通过拆主张数量降低成本指标。
- 真实总 tokens 可能受 60 万地板约束而不下降；应检查有效覆盖和每个正确要点成本，不能仅因 tokens 更少宣称更好。旧故障高耗样本不能用于制造夸大的效率提升。

最终结论只能是：实现通过/未通过、评测可用/仍待复核、质量改善/未改善/证据不足。三项分别写明；不要求为了完成本轮而把结果包装成成功。
