# 纯程序化验证与验收实施计划

状态：已实施，本地程序化验收通过（2026-09-11，macOS arm64 / Node v24.18.1）。完整结果见 [实施与验收记录](programmatic-verification-results.md)。下文保留制定时的分析、范围和验收要求；历史基线与本轮实际结果分别记录。

## 1. 目标与范围

用户已明确：修复是否完成只通过程序化验证判断，不依赖真实模型达到某个语义准确率。这一要求替代前几轮“先通过真实模型校准才能完成工程验收”的安排；不能通过修改旧校准结果或降低旧门槛实现。

本轮目标：面对任何符合或不符合协议的模型输出，程序都按明确合同处理；输入、引用、状态、预算、恢复和算分可复现；模型判断不能被包装成程序证明。模型可以答错、遗漏、拒绝或前后矛盾，这些情况本身不代表程序测试失败；程序没有按预期拒绝、记录、隔离或停止才是失败。

本轮包含：benchmark 验证入口和数据合同、确定性流程缺陷、来源标记传播、门槛拆分、离线验收工具和跨模块回归。研究引擎的输入/证据/发布/恢复合同纳入回归，但不重构探索策略和报告生成，也不修改探索 token 下限。

执行门槛迁移仅作用于 benchmark 实验工具；普通 `jdr research` 和研究 API 不新增“必须携带程序验收文件”的使用条件。

不包含：新语义解析器、自然语言证明系统、多模型投票、新增语义审核层、提高模型准确率、调参或模型选型、真实 Google 调研、旧报告实模重评、实模报告重建、新一轮真实模型校准。用户后续明确执行某种真实实验时，才运行对应命令。

## 2. 现有功能与问题定位

| 模块 | 当前功能 | 本轮处理 |
|---|---|---|
| `scripts/benchmark-quality.mjs` | 分发校准、评分、重建、比较和实验；score/rebuild 硬依赖 requireCalibration | 新增零外部调用的程序验收入口；新执行条件与模型分数分离；读取设置和创建 provider 延迟到真实操作分支 |
| `quality/calibration-suite.mjs`、`calibrate.mjs` | 冻结代码、模型、样本及预算，并根据模型命中率授予校准资格 | 保留历史语义和原失败记录；不再作为新工程验收前置条件 |
| `quality/load-result.mjs`、`locators.mjs` | 验证固定 revision、manifest、正文、引文位置和来源身份 | 复用为纯程序检查，明确证明范围只到产物/引用完整性 |
| `quality/judge.mjs`、`item-review.mjs` | 回执持久化、JSON 处理、ID 合同、重试、组件缓存与恢复 | 保留；修复顶层 ID 错误被泛化后丢失纠错细节的问题 |
| `quality/relation-decision.mjs` | 决定、依据审核、一次修复与终审 | 模型关系与审核结果单独标来源；阻止相同决定通过后一次审核翻转消除原分歧 |
| `quality/assertion-bindings.mjs` | 逐出现位置审核及补上下文 | 分离原文绑定完整性与模型忠实性判断；合法零新增可正常结束程序处理；用区间并集判断实际新增 |
| `quality/relation-components.mjs` | 事实/引用任务、材料检查及确定性汇总 | 保留来源隔离和聚合规则；候选结构失败不能被当成材料缺失；不在本轮做跨任务语义缓存重构 |
| `quality/report-facts.mjs`、`report-context.mjs` | 模型提取、逐行审核、有界上下文和出处绑定 | 已提供块、ID、区间可程序检查；断言是否全部提取、上下文是否充分仍属于模型观察 |
| `quality/evaluate.mjs`、`score.mjs` | 把模型判断聚合为覆盖、准确率、引用支持率与质量门槛 | 保留既定算术；明确指标依赖模型输入，移除“算术可验证＝内容质量被证明”的歧义 |
| `quality/improvement-gate.mjs`、`rebuild.mjs` | 校准及模型覆盖增益决定是否可继续实验、重建 | 新路径按程序验收、输入、计划、预算检查执行条件；模型改善只作描述性观察 |
| `quality/compare.mjs` | 读取评分、比较版本集合并汇总有限数值 | 分开程序检查与模型指标；按 case/repeat/实际来源逐项配对，保留全部计划分母 |

当前工程基础已覆盖大量定位、恢复和账本行为。上一轮 1,155 个测试通过属于历史基线，本次没有重新运行。测试中的默认 faithful/support/mock oracle 答案用于控制程序分支，不能作为模型质量证据。

## 3. 明确三种结果，禁止互相替代

### 3.1 程序验收

新增 `programVerification`，证明指定代码版本在固定合同案例、故障序列和回归检查下满足程序不变量。

- `status: passed | failed | incomplete`。
- 固定 `verificationVersion`、代码/依赖/测试/案例 manifest 哈希、运行环境、检查 ID、实际执行结果、日志或结果文件哈希。
- 记录实际外部派发数及意外外部调用尝试数，验收要求均为 0；真实模型和搜索/抓取不得实际调用。负向场景中预注册、在 transport 派发前截断的探测单列为 `expectedBlockedAttempts`，逐项断言确实被阻断，不能拿该分类豁免其他外部调用。
- 由实际 runner 生成，不能仅消费手写的 test/lint/build passed 布尔值。
- 必需检查遗漏、超时、被跳过、结果损坏或依赖缺失，不能写 passed。适用性由固定案例注册表决定，不能在失败后把必需项改成不适用。
- 哈希用于验证本地结果身份和一致性，不宣称具有抵抗任意本地文件伪造的远端认证能力。

### 3.2 单份产物的程序检查

独立 `artifactVerification`，验证指定 resultRevision 的 manifest/正文/引用/已声明绑定/可观测账本是否符合合同。它不是全仓库测试证书，也不是内容准确率。

可以产生的检查包括：正文 hash 匹配、引用注册表闭包完整、引文等于原始 UTF-16 区间、绑定属于同一报告/指定来源版本、保存的计数可由账本重新求和。

必须写明范围：检查的是“已声明的引用和绑定”，不是证明报告没有遗漏任何事实；某材料被提供过，也不是证明模型理解了全文。

### 3.3 模型观察

模型产出的 relation、basis、coverage、faithful、qualifier、truth，以及由其派生的语义分数统一属于 `modelAssessment`。

- 逐事实、绑定、关系及汇总都能追溯 `origin: model_assessment`；不能仅在顶层写 machine_draft。
- 模型流程状态与程序验收状态独立，模型待审或错误不使正确处理该情况的程序测试失败。
- 顶层不再生成笼统 `qualityTargetMet`。保留 `modelThresholdsMet: true | false | null` 作为模型观察字段；未观察为 null，不能当成 0、false 或通过。
- 来源类型区分 `model_assessment`、`scripted_fixture`、`program_check`、`program_oracle`、`human_review`。聚合不会提高来源的证明等级；人类复核需真实记录，不能自动生成。
- 程序只对自己执行的检查字段背书。Provider 返回 programVerification、humanReviewed 等字段，不能覆盖程序拥有的结果字段。
- 自然语言“成功读取多少次”若先由模型映射到字段，即使后续数值比较是确定性的，整个判断仍依赖模型映射。缺少成功正文读取计数时保持 unavailable，不能以 sourceReads 或文档版本数代替。

## 4. 实施步骤

### P0：保留当前基线与明确合同

1. 核对现有未提交工作区、v8 冻结源码副本、结果和恢复验证摘要；保存本轮实施前文件 manifest。
2. 不覆盖 v5–v8 样本、oracle、曝光账本、模型回执、预算或研究结果。新验证产物进入新的本地忽略目录。
3. 建立固定的不变量/场景注册表，列出每项规则、输入、预期行为、独立判据、适用范围、对应测试。以场景是否覆盖验收，不以测试总数增加验收。

交付：范围与不变量表、基线身份记录、明确列出的必需验收场景。

### P1：分离数据合同与判断来源

修改 `schema.mjs`、`evaluate.mjs`、`score.mjs`、`report-facts.mjs`、关系与绑定封装、CLI 输出和比较读取；新增小型 `verification-contract.mjs` 管理程序检查结果及来源规则。

1. 新增程序验证 schema/version，与 judgeVersion、scoringVersion 分离。新评估 envelope 使用新 schema，不能原地改写旧 score.json。
2. 将原文定位/来源检查结果与模型忠实性、语义覆盖结果拆开。例如 `bindingIntegrity` 只说明已声明位置有效，`bindingAssessment` 保存模型判断；不把已有 bindingComplete 偷换成程序完整性。
3. `relation confirmed` 在新输出中明确为模型流程已给出可用判断，不代表程序已证明关系成立；保持原回执、判断记录和分歧可追溯。
4. 分数公式继续测试其“给定判断时”的计算正确性，模型决定的分母、事实集合、类别和正确率都保留来源。结构化账本计数与模型语义分数分栏输出。
5. 实施来源传播规则，贯穿保存、恢复、聚合、导出和比较。格式合法但语义错误、甚至多轮一致错误的响应，只能生成模型观察。

验收：固定错误语义响应贯穿全链路后不会产生程序真值证明；模型输出无法设置程序通过或人类已复核；工程通过与模型观察失败/未运行可同时存在。

### P2：修复确定性的控制流缺陷

#### P2.1 精确 ID 错误反馈

- 在 `judge.mjs`、`schema.mjs`、`item-review.mjs` 之间传递有类型的安全结构错误。
- 反馈包含字段、允许 ID、缺失已知 ID、重复已知 ID、未知 ID 数量；不回写任意未知 ID、provider 自由文本或错误正文。
- 顶层 ID 校验失败也写入持久化结构反馈；第二次结构请求拿到具体纠错信息。
- 不自动猜 ID、补判断、删错项或重置次数；`item-review` 继续独占每项最多两次结构尝试，保留已接受兄弟项及原派发回执。

#### P2.2 无进展修复不能清除既有分歧

- 给关系决定和单条依据建立规范化指纹，包含主张/材料依赖、来源版本、原文范围、关系和 basis；排除数组顺序、定位选择器别名、显示 ID 等表现差异。
- 重复、重新排序或等价拆分相同原文范围不算新依据。比较依据按相同来源与关系分组，不能把不同来源或不同主张合并。
- 修复前后决定无实质的结构变化：记录 `repair_no_progress`，保留模型分歧，跳过最终模型审核。
- 部分改变时，仍存在的相同被否定依据不能因为其他部分变化而被重新放行。原始否定记录继续参与模型流程的 pending 状态。
- 这项规则只证明“程序没有靠再次抽取回答洗掉分歧”，不认定第一次模型审核正确，也不证明发生变化后的语义判断正确。

#### P2.3 绑定零新增与区间规范化

- 精确区分非法 `{bindings:[]}` 与合法逐 ID `{contextLocators:[]}`；明确提示词中的空数组字段，不改变 ID 完整性要求。
- 同一 reportHash 下用原始 UTF-16 区间并集计算是否增加覆盖位置。相同区间、已有区间子集、重复或重新分段不算新增。
- 合法无新增作为 `completed_no_change` 结束程序修复分支，保留模型原判断，不触发重复语义审核，不将其当格式失败无限纠错。
- 已声明绑定的原文完整性可以通过；模型的 missing_context 可以同时保留。由此解除“模型第一次误判就使工程验收永远失败”的耦合。
- 真正新增位置才使依赖失效并允许原有有界终审。新位置仍只证明新增原文存在，不证明它是语义上必要或充分的上下文。
- 本轮不引入“模型证明自己无需补充”的新裁决层。

#### P2.4 辅助步骤、前置失败与诊断输入

- 候选定位建议格式失败且用量已知、原材料完整时，可以用空候选进入既有全文判断；保留候选失败诊断。预算暂停、未知调用、材料损坏不能被此退路绕过。
- 对绑定模型判断尚未完成的出现位置，默认保留待审并暂停其自动下游模型调用；其他有效项继续。待审项留在原分母，不能通过跳过来提高成绩。诊断性额外核验若保留，必须显式选择且单列。
- 诊断入口保留明确输入的 kind，不把 attribution 无条件改成 fact；不把 fixture 预设类型当成模型已经正确提取类型的证据。
- 既有“基础设施暂停优先”“最后一项暂停不能变 finished”等规则继续保留。

验收：全部使用预定响应脚本验证派发顺序、次数、持久化状态和结果；不要求模型实际生成任何指定判断。

### P3：建立离线程序验收入口

新增 `program-verification.mjs` 与固定场景注册表，提供 `runProgramVerification()` / `requireProgramVerification()`。CLI 新增 `verify-program`，npm 增加 `verify:programmatic` 指向同一入口。

命令约定：

```text
node scripts/benchmark-quality.mjs verify-program --output-dir <local-dir>
node scripts/benchmark-quality.mjs verify-artifacts --campaign <file> --output-dir <local-dir>
```

- `verify-program` 执行必需离线场景、现有全量测试、lint、build、diff check，并生成程序验收记录；不能把实模 calibrate 包装在内部。生产分派器用依赖注入测试，场景 worker 独立运行，避免 verify→npm test→verify 的递归。
- 新 checkout 没有任何已有验收记录时也必须能运行。门槛校验与评分/重建执行器分层：分别测试真实 validator，执行器测试注入受控上下文，CLI 接线测试覆盖拒绝与通过分支；不能为自举先写一份正式 passed 占位记录，也不能给生产 CLI 增加隐式跳过门槛开关。
- `verify-artifacts` 只读取固定 manifest/revision 并执行机械检查，不创建 Judge、不加载模型设置、不访问搜索或抓取；新输出目录不能覆盖原研究目录。它不替代全仓库程序验收。
- 使用真实 runner 的退出码、结构化测试结果、固定场景 ID 和产物哈希决定 passed；stdout 的一段“passed”文本不构成证明。
- 返回码 0 仅用于必需检查完成且通过；失败、环境未满足、必需结果缺失返回非零，并区分 failed/incomplete。
- 模型配置和密钥缺失不影响程序验收。所有外部依赖注入，未声明调用立即失败；原始 API 配置不进入验证记录。
- 验收运行时禁止外部网络及真实模型/搜索进程。既有网络协议测试可使用测试自身创建的回环 fake server；须单独计数，不能把“零外部网络”写成没有任何本地 socket。
- 工具层守卫覆盖 fetch、直接 Undici、http/https/http2、net/tls、DNS 与真实 provider/search 适配器；守卫传递到所有 Node 子进程，只允许注册的测试服务与受控命令。Linux CI 在依赖安装后用 OS 网络隔离禁止外网并保留测试回环；原生或子进程通路无法由工具层封闭时必须使用等效 OS 隔离。不能仅凭 fetch 被 mock 就声称所有网络通路都被禁用；本地环境无法完成隔离检查时，该必需项为 incomplete，其他检查可单独报告。依赖安装属于验收准备阶段，失败则 incomplete，不在运行阶段临时下载修补。

程序验收记录至少包含：schema/version、固定场景 manifest、代码/依赖/测试身份、Node/OS、必需检查列表、实际执行结果、失败种子或安全故障序列、外部调用计数、日志哈希、最终状态。重新运行同一代码可产生新时间戳和记录文件，但稳定的实现身份不变。

### P4：拆开工程门槛与模型观察

修改 CLI、`improvement-gate.mjs`、`rebuild.mjs` 和相关读取接口。

| 操作 | 新流程条件 | 结果含义 |
|---|---|---|
| 程序验收 | 固定代码与依赖可执行离线检查 | 程序在指定合同下行为正确 |
| 产物检查 | 输入 pin/manifest 存在且可验证 | 已声明产物及引用结构完整 |
| 模型评分观察 | 用户明确选择模型观察、当前程序验收有效、输入/预算有效 | 该模型在该输入上的描述性判断 |
| 报告重建 | 当前程序验收、合法原始正文和 pin、冻结计划/预算/输出隔离 | 使用既有正文执行重建，不证明质量提升 |
| 新真实调研 | 用户明确执行 run、当前程序验收、配置身份/搜索通道/预算/恢复边界有效 | 实验可以执行，不证明调研质量达标 |
| 模型改善比较 | 实际可配对的同口径观察结果 | 模型评分的变化，不决定工程是否验收 |

具体调整：

1. 保留旧 `requireCalibration()` 的严格语义，不改成恒 true，也不把旧校准失败改成通过。新路径调用 `requireProgramVerification()`。
2. 新 `score` 必须显式选择 `--mode model-observation`；引用 `--program-verification`，不要求真实模型校准命中。现有 `--calibration` 旧模式维持旧语义，与新模式参数混用时明确拒绝，不能静默降级后付费调用。
3. 新重建使用 `requireRebuildInputs()`，验证所选原始输入和程序记录，不再要求所有基线模型评分已完成。保留正文完整性、禁止搜索抓取、禁止覆盖原结果、锁、累计预算和 floorApplicable=false。本轮保留既定四份首轮样本选择，不扩展实验范围。
4. `assessProgramExecutionGate()` 只检查程序结果与实验输入条件；`assessImprovementObservation()` 单独报告模型变化。新 gate 不写含混的 canLaunchLive，使用明确的 eligible 与条件列表；eligible 不自动启动任务。
5. 新 campaign/gate config 显式引用程序验收及其 schema。旧 validationGate 按旧 schema 处理，不能自动转换；迁移只写新配置，不改旧 campaign。
6. 原 10pp 模型覆盖增益和模型校准命中率不再阻塞新工程验收或工程执行条件，也不能因工程通过而宣称达标。用户未来另设产品质量目标时，独立记录其依据。
7. 程序验收记录引用只作执行前置与来源元数据，不加入模型请求内容或模型缓存身份。重复生成同一代码的证书不能引起相同模型请求重发。输入、模型、协议、真实依赖变化仍使对应缓存失效。

### P5：输出、历史兼容与文档

1. 新评估 schema 与 program-verification schema 独立；judge/关系/绑定协议如因 P2 发生变化，升级相应版本及缓存身份。算分公式未变时不凭空改变公式版本。
2. 原 v5–v8 校准和 score 只读展示为历史模型观察；不得改名成程序验收、迁移原账本或复用不兼容旧回执。继续旧冻结运行必须使用原代码环境；新代码明确拒绝混用。
3. `summary/compare` 分别显示计划、交付、产物检查、模型完成、模型待审、未观察数量；缺失为 N/A，不能筛掉未完成样本只展示有利分母。
4. 模型比较按 case/repeat、rubric、模型/协议和来源逐项核对；每份 score 必须绑定其自身 resultPin，全局身份集合相同不足以证明正确配对。重建比较验证 candidate.inputPin 对应 baseline.pin，不要求重建前后的输出 resultPin 相等；独立真实运行按冻结实验设计配对各自输入，不能强行要求报告 revision 相同。交换两个案例的模型身份必须被检测。
5. 新脚本化验收产物带 scripted_fixture 标记，不能传给真实校准/模型观察入口，不能更新真实曝光账本。
6. 更新 AGENTS.md、README、benchmark README 和 CLI help，明确纯程序验收是本轮完成条件、真实模型效果另行观察。保留历史失败说明，不删除不利结果。

## 5. 确定性验收矩阵

| 编号 | 注入情况 | 独立预期 |
|---|---|---|
| V01 来源不升级 | 所有模型步骤给出格式合法、语义错误且一致的通过回答 | 程序可保存模型观察；事实、绑定、分数、恢复和导出均不出现程序语义证明 |
| V02 结果独立 | 无模型配置；模型观察未运行、全部错误或待审 | 程序验收依据程序检查决定；不能要求模型命中率；程序合同失败不能被模型满分覆盖 |
| V03 ID 合同 | 缺失、重复、额外、未知 ID；顶层空列表 | 准确安全反馈，次数不超过原帽，合法兄弟项不重发，不伪造判断 |
| V04 无变化关系 | 首审拒绝，相同依据修复，预设终审会同意 | 终审不调用，原分歧保留；数组顺序、显示 ID、定位别名不绕过 |
| V05 部分变化 | 只修改一个依据，保留另一个被否定依据 | 保留的同一分歧不能被其他修改洗掉 |
| V06 绑定进展 | 空补丁、完全重复、子区间、旧区间重新分段 | 程序合法结束或按明确合同拒绝；无新增覆盖不触发重复审核、不自动 faithful |
| V07 真实新增绑定 | 新位置、跨段、表头、相同文本的另一出现位置 | 按来源位置与区间并集判断进展；不按字符串相同去重不同出处 |
| V08 来源隔离 | 异报告同文、不同版本、错误 owner、未展示块 | 拒绝越界锚点；完整性错误不能以嵌套 findings/旧正文补救 |
| V09 字符边界 | UTF-16 代理对、重复 quote、重叠/相邻区间、超大 owner | 原文精确定位；歧义有界处理；不截断材料凑预约 |
| V10 候选退路 | 已知用量的候选格式失败；另测未知调用/坏正文 | 前者保留诊断并可用全文；后者仍暂停，不借空候选绕过 |
| V11 前置待审 | 一个绑定待审、另一个有效 | 前者保留分母与原因且不自动浪费下游调用；后者可继续 |
| V12 预算 | 确认零值、未知用量、预约不足、拆批、重试、最后一项暂停 | 未派发不耗尝试；未知预约保留；不借阶段额度；暂停不写 finished |
| V13 恢复 | 请求前后、响应落盘未结算、部分接受未清 flight、晚回执、重分组 | 原请求与依赖不变；已接受项不重跑；回执只结算一次；旧依赖不串新材料 |
| V14 算分 | 固定 judgment/criterion/citation 集，空分母、冲突、部分分、待审 | 与独立公式一致；算术通过不提升模型语义证明等级 |
| V15 指标 | 缺字段、0、未知、同数值不同含义的计数 | 未知不当零；读次数不冒充成功正文次数；模型映射仍标模型来源 |
| V16 发布读取 | 缺文件、错 hash、旧指针、新旧 revision 拼接、损坏证据 | 固定版本闭包检查拒绝；原子结果与数据库提交语义保持 |
| V17 重建 | 无模型评分但正文完整；坏 manifest；覆盖原路径；搜索调用 | 合法输入可做脚本化重建；其余拒绝；无真实外部调用 |
| V18 门槛拆分 | 程序通过/模型失败，程序失败/模型满分，旧 schema 混入 | 新程序门槛只按程序条件；旧字段不静默转换，eligible 不触发执行 |
| V19 比较 | 案例身份互换、不同 rubric、待审、未运行、合法重建产生新 revision | 按项核对 score 自身 pin 与实验输入关联；合法新输出可比较；拒绝不兼容比较并完整列出分母 |
| V20 验收记录 | 无已有证书的新 checkout；手写 passed、缺必需场景、代码变化、损坏结果、环境缺失 | 无证书可自举运行全部验证；其余无效记录不能获准；新时间戳不改变同代码缓存身份 |
| V21 外部调用 | 禁用/清空凭据；预注册探测诱发 provider/search/网络路径 | 在 transport 派发前阻断并计入 expectedBlockedAttempts；实际外部派发及意外尝试均为 0；回环服务只允许测试自身创建的实例 |
| V22 引擎合同 | 模型新增硬需求、snippet 冒充正文、反证/支持矛盾、未完成 slot | 依据原请求、ID、证据和既有明确规则处理；不让 benchmark 改造破坏引擎合同 |

增加统一 scripted provider：按 purpose、请求形状、尝试序号匹配预设响应或故障；未知调用直接失败，不能根据生产函数当前输出动态生成“总能通过”的答案。保留原 14 份完整报告模拟为接线与算分测试，明确不是语义准确率测试。

增加固定种子故障序列：默认 64 个种子、每个最多 40 步，覆盖派发、拒绝预约、回执、结构错误、逐项保存、重启和依赖变化。参考状态机只用独立集合、计数和状态表；每一步校验，失败保存种子与安全操作序列，可缩减为固定回归。

回执重放使用生产 Judge/解析/账本路径，provider 设置为调用即失败。提交的 fixture 使用合成或脱敏回执，不把本地原始调研正文搬进仓库；真实 v8 回执可作额外只读诊断，但不得成为新机器验收所必需的私人文件。

程序 oracle 优先使用区间、集合、账本、哈希、真文件系统与锁、原子发布及固定公式。现有 SQLite oracle.c 不自动纳入本轮门槛：未建立离线固定版本依赖与 wrapper 前不能宣称该域实验已覆盖，更不能下载或改用宿主版本充数。

## 6. 测试与 CI 执行顺序

1. 每个 P1/P2 改动先运行相关定向测试，验证实际生产函数与生产 Judge，避免只测试新 helper。
2. P3/P4 完成后运行场景矩阵、固定种子、重放与脚本化 CLI/重建集成；允许预期失败场景通过测试，但其业务结果必须保持失败/待审。
3. 最终以统一入口完成全量 npm test、lint、build、diff check 和固定验收场景，生成新程序验收记录；不另跑真实模型作为收尾步骤。
4. `.github/workflows/ci.yml` 保留 Node 20/22 矩阵，改为调用统一验收入口，避免重复执行同一套全量检查。安装依赖在隔离验收之前；CI 不注入模型/搜索凭据。
5. Linux 的 OS 锁/进程恢复与本地 Node 版本分别记录。尚未运行的 CI 不能在本地结果中标通过；环境无法运行的必需项明确 incomplete。
6. 验证产物只发布安全检查摘要、身份与失败代码；原始 prompt、正文、自由推理、API Key、本地运行目录内容不得进入提交或公共 CI 产物。

## 7. 完成标准与分批提交边界

建议实施批次：A 数据合同与来源传播；B 确定性流程修复；C 离线 runner 和验收记录；D 门槛/重建/CLI/比较迁移；E 集成、CI 与文档。每批有对应回归后再进入下一批，不把所有变更集中到最后验证。

完成必须同时满足：

1. V01–V22 必需场景及固定种子全部完成；全量测试、lint、build、diff check 通过。
2. 程序验收不读取真实模型配置、不调用真实模型/搜索/抓取，实际外部派发和意外外部调用尝试均为 0；预注册阻断探测另行核验。
3. 关系无进展、绑定区间进展、ID 反馈、预算与恢复均符合预写规则。
4. 任意合法但错误的模型判断，在保存、恢复、聚合和展示后都不升级成程序语义证明。
5. 新工程路径不依赖真实校准命中率，也不把工程通过当成研究质量达标；旧模型门槛和历史结果不被伪装成通过。
6. 输入 revision、正文、引用和已有用户需求合同保持；原结果、v8 账本/曝光记录及冻结产物未被改写。
7. 最终交付说明哪些程序行为已验证、哪些模型语义没有验证；明确没有运行真实调研或模型校准。

本次请求范围是分析和规划。实现改动、测试和真实实验均未在本次执行；后续实现本计划也不包含自动提交、推送、合并或启动付费实验。
