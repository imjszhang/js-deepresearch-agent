# 第三轮修复计划：程序定位、模型判断、冻结校准

状态：待实施。本次只核对代码与历史校准状态、制定计划；没有修改评测程序、迁移 fixture 或调用真实模型。

执行起点是当前工作区中尚未提交的 v5 实现，不能从 HEAD 重新覆盖这些改动。上一轮记录见 [第二轮实施与结果](calibration-round-2-results.md)。

## 1. 目标与范围

把精确位置计算从模型移到程序，保留严格的正文、版本、引用和断言校验；同时澄清读取次数的计量语义，再执行一个冻结的 v6 候选。

本轮包含：

1. 统一报告断言、共享条件、技术证据和引用证据的定位合同。
2. 程序生成位置与片段编号，模型选择片段并判断语义。
3. 有界处理重复摘录、错误选择及恢复，提供可操作的结构错误码。
4. 区分阅读预算计数与成功正文读取计数，修复缺失指标的处理。
5. 完成离线验证、固定开发集回归，通过后执行已有的 34 个未实模执行的留出样本。

不修改调研运行器、探索强度、计分公式、Redis/SQLite 金标准或旧评测结果。本轮不执行旧 7 份报告重评、4 份固定正文重建和 8 次 Google 调研，不自动提交、推送或合并。

## 4. P1：建立由程序生成的定位目录

新增共享定位模块，供报告提取与证据核验使用，避免各阶段分别实现 indexOf 或偏移换算。

### 目录与选择合同

程序保存两层数据：

| 层 | 字段与职责 |
|---|---|
| 文本归属 | 报告 hash 或正文版本、source/evidence/passage ID、原始文本 hash、局部到原文的基准位置 |
| 可选择单元 | 稳定 unit/fragment ID、原文摘录、程序计算的 UTF-16 区间、容器及上下文关系 |

模型返回定位选择，例如 `unitId + quote`，或一个已经提供的 `fragmentId`。不再要求模型生成 span、start、end 或 contextSpans 数字；共享条件通过 context locator 列表选择。

解析规则：

1. 只在模型选定、且本次输入确实提供的单元内精确匹配 quote。
2. 恰好一次出现：程序计算位置并复核原文切片；归属、版本和范围必须一致。
3. 多次出现：程序生成带区分上下文的候选位置 ID，在本阶段剩余尝试额度内要求明确选择。模型不负责计算出现次数或偏移。
4. 找不到摘录、选错文本归属、候选 ID 不存在或仍有歧义：保持待审，不能扩大到其他文档搜索或默认取第一次出现。
5. 选择上下文只表示读到了该片段，不能自动作为支持证据；支持、反证与条件关系仍要单独判断。

规范输出继续包含精确 quote/span、原文归属、正文版本、引用键和上下文位置，并附 locator 版本与目录 hash。现有逐断言 oracle 继续核对这些由程序生成的位置。

### 分段与边界

- 按行、句或子句生成可寻址单元，单元只是阅读容器，不预判其是否包含事实。标题、表格和参考文献中的实质断言仍需审计。
- 替换目前每 7,000 字符机械切块的做法：批次大小与文本定位单元分离，不能切断代理对、丢掉行尾或让表头与数据行失去关系。
- 长单元可以提供相邻窗口及稳定上下文连接；批次裁剪或预算不足不能被写成完整检查。
- 单条断言的主要摘录保持连续；跨句条件和多份证据分别记录，不能拼接文字后冒充原文中的连续区间。
- 使用原始文本计算 UTF-16 位置，保留 CRLF、空格、全角符号、组合字符和 emoji。不得通过模糊匹配或 Unicode/空白归一化悄悄改变事实锚点。
- 同一句内存在多个断言时仍须提供各自足够精确的主要摘录；相同的宽泛片段不能替代多个原子断言的定位与校验。

## 5. P2：接入提取、补提取和证据关系验证

### 报告提取

`extract → 定位解析 → 覆盖审计 → 最多一次遗漏补提取 → 定位解析 → 最终覆盖审计`

- 事实 ID 根据规范化后的真实位置及内容生成，不根据模型猜测的数字生成。
- 每个出现位置保留自己的引用和上下文。重复命题可以合并展示，但每次出现都参加遗漏和 oracle 检查。
- 定位解析的歧义修复属于当前提取阶段的结构修复，不另开一个无限次数的模型阶段。
- 同一块中已成功定位的候选应暂存；另一候选定位失败时保留有效部分，整体仍为不完整。后续结构修复不得让有效候选消失或重复计入。
- 定向补提取只处理审计确认遗漏的单元；unknown 不自动触发再生成。替换旧候选必须声明关系并重新审计受影响范围。
- 模型选择了正确位置但改变了命题、版本、否定或条件，依然属于语义错误；定位成功不代表提取忠实。

### 技术证据与引用

- `goldContext` 和 `citedEvidence` 的每份可核验文本都生成对应目录；保留 gold 原文位置、passage 局部位置到正文原文位置的映射。
- 模型选择证据片段并返回 full_support / partial_support / contradiction / not_addressed / uncertain；程序解析位置后沿用 v5 的真值映射。
- 正确事实可以引用错误来源；引用支持只能使用该引用键绑定的正文片段，不能借 gold 或另一个引用的证据补足。
- 只选整份手册的 ID 不能自动证明某个原子主张。仍需定位到实际支持或反驳的内容，审核对象、版本和条件。
- 保留支持与反证冲突，不因选择了一个支持片段就删除反证。未检查全部相关输入时不能声称“不存在证据”。
- 目录不能通过只保留预测有利的片段隐藏原本提供的证据。输入过长时分批处理，完整性状态独立记录，不为节省预算截掉困难材料。

重点文件：`report-facts.mjs`、`evaluate.mjs`、`evidence-relations.mjs`、`load-result.mjs`、`judge.mjs` 的输出字段白名单，以及新增定位模块。

## 6. P3：修复运行指标的语义绑定

建立小型、版本化的执行指标定义表，将“这是什么指标”与“本次是否有该指标值”分开。

至少区分：阅读预算计数、成功正文读取次数、正文版本数、passage 数、已确认探索 token、探索下限状态和报告完成状态。每个定义包含单位、计数对象、取值规则、可信来源及 known/missing/unknown 状态。

处理流程：

1. 模型识别原句谈的是哪种指标及所声称的数值或状态。指标值缺失不等于指标含义不明确。
2. 程序从有定义的可信字段读取对应观测；不能把 `sourceReads` 自动映射为成功正文读取次数。
3. 指标明确且值已知：程序比较；指标明确但无可靠记录：unverifiable；指标含义或记录完整性仍不确定：pending_review。
4. unknown 和 missing 均不得当成零；记录的零必须有明确来源和完整计量范围。

对于当前没有完整成功次数记录的历史产物，本轮暴露一个定义明确但值为 missing 的成功正文读取指标。不给旧结果补造计数，不以文档数、HTTP 200 数量或零散 successfulReads 事件相加替代它。

已有成功动作记录可以作为语义调查材料；本轮不扩大到实现所有旧格式的事件重建。若未来需要提供真实成功总数，另行定义完整执行段、成功标准、重试/恢复去重和来源证明。

`v4-h19` 原句及 unverifiable 预设保持。离线同时验证“预算记了 3 次”“成功读了 3 次”“保存了 3 个正文版本”在不同已知/缺失观测下不能混用。若对原句计量对象仍无法达成可审计解释，记录为协议问题并阻止冻结，不能为过关强制给模型指定答案。

重点文件：`statements.mjs`、`evidence-relations.mjs`、执行指标定义模块及相关 fixture 说明。运行器本轮只读。

## 7. P4：有界错误处理、恢复与身份

- 保留 v5 每阶段每项目最多两次派发、一次语义补提取的上限。批次拆分、位置消歧与恢复共用原尝试计数，不叠加额外额度。
- 结构反馈使用白名单错误码，例如 `locator_unknown_id`、`locator_quote_not_found`、`locator_ambiguous`、`locator_owner_mismatch`、`locator_catalog_mismatch`；歧义反馈只包含必要候选 ID。诊断汇总不记录自由推理、密钥或报告正文。
- 原始安全结构化响应和解析后的规范事实分别保存，便于区分模型选择错误与程序解析错误。
- 检查点绑定报告/正文 hash、目录 hash、locator 版本、模型和 judge 身份；同一原文同一版本在不同批次划分下仍生成相同单元 ID。
- 在模型响应落盘、位置解析、候选暂存、审计和评分等边界中断时，可以复用已有响应重新解析，不能重发或双结算。
- 代码、目录版本或文本发生变化时，不复用旧版已接受事实与校准证书。旧缓存不迁移为 v6 成功结果。
- 正式评分、rebuild 和 live 门禁同步校验 v6 协议、目录版本、代码/模型/suite 身份及完整校准结果。仅提取定位测试通过不能放行。

重点文件：`item-review.mjs`、`judge.mjs`、`schema.mjs`、`calibration-suite.mjs`、`calibrate.mjs`、CLI 与门禁消费者。

## 8. P5：离线验证及样本处理

### 必测矩阵

| 类别 | 验收要求 |
|---|---|
| 精确定位 | 中文、英文、emoji、组合字符、CRLF、表格和代码文本的规范 span 均与原文切片一致 |
| 重复与歧义 | 同句多次出现、同文本不同版本、同段重复短语只能绑定明确位置；没有唯一选择时不猜 |
| 越界与伪造 | 不存在的 ID、错 owner、错目录 hash、改写 quote、跨引用借片段都拒绝 |
| 分段上下文 | 长行、7,000 字符附近、跨句条件、表头与数据行不丢上下文；批次变化不改位置身份 |
| 断言完整性 | 混合真假、建议前提、事实标题、重复出现及必要条件完整保留；宽 quote 不替代多个原子断言 |
| 定位与语义分离 | 锚点真实但命题改写、版本错误或反证关系错误，仍不能通过 |
| 有界修复 | 歧义在剩余额度内修复；失败候选不丢有效兄弟候选；没有额外语义补提取循环 |
| 执行指标 | 预算计数/成功次数/文档数独立；已知零、缺失和 unknown 的结果正确 |
| 恢复 | 每个持久化边界中断后零重复派发和结算；目录漂移拒绝；未知预约保留 |
| 评分与门禁 | 14 份报告的完整生产评分流程仍通过离线模拟；旧证书改版本号、待审快照和仅定位通过都不能放行 |

v5 的实际失败摘录可以转为定位器离线回归材料，但只使用能够独立确认原输入归属的记录。不能在全部报告里搜到一句相似文本就认定位置恢复成功；输入无法还原的记录标为不可用。离线回放不发送模型请求，也不改写 v5 输出，不将离线定位通过称为真实语义校准通过。

### 校准数据

- 固定 20 个开发样本的原文、顺序和预期真值保持；继续逐项对照 v5，不删困难样本。
- 34 个现有留出样本可以沿用：当前已确认未实模执行，实施时再次核对注册表、账本和结果目录。声明为“预先设计、尚未实模执行的留出”，不称实施者未知的全新盲测。
- 复制原文件到 v6 suite 的合法目录范围，核对原文、证据和 oracle hash 一致；保留原样本 ID 和来源，不靠改名制造新样本。wrapper 单独更新协议版本。
- 暴露记录增加 v5 实际执行的 20 个开发样本及轮次，不把未调用的 34 个样本误标为已测试，也不删除原有 60 个历史样本的记录。
- 位置计算迁移不改变 oracle 的 span/allowedSpan/requiredSpans。若发现确凿的预设答案错误，首次调用前单独记录依据、保留原版及影响，重新冻结；不得观察本轮模型结果后改答案。

完成相关离线测试后运行完整 npm test、lint、build 与差异检查。新提交同步后再要求 Linux Node 20/22 CI 通过；本地绿灯不冒充远端 CI。

## 9. P6：一次冻结的真实模型校准

首次调用前保存计划文档 hash、工作区文件清单/代码 hash、锁文件、定位目录协议、执行指标协议、suite/证据/oracle/暴露注册表、实际模型参数、阶段顺序、预算和离线验证结果。本轮补齐 v5 未在首次调用前记录计划 hash 的流程缺口。

默认沿用 `qwen3.8:27b-mlx`，temperature 0、reasoning none、每次输出上限 4,500 token；调用前核对实际配置。凭据不落盘或展示。不安排额外真实模型调试调用。

| 阶段 | 样本数 | token 上限 | 累计模型调用墙钟上限 | 进入条件 |
|---|---:|---:|---:|---|
| 固定开发回归 | 20 | 60,000 | 15 分钟 | 离线验证及冻结完成 |
| 断言留出 | 20 | 70,000 | 20 分钟 | 开发回归 20/20 |
| 完整评分留出 | 14 | 90,000 | 25 分钟 | 开发回归通过，且没有预算/环境/未知调用阻断 |
| 合计 | 54 | **220,000** | **60 分钟** | 一个 v6 冻结候选 |

额度为下一轮计划上限，不是消耗目标，不沿用 v5 余额。单次请求仍最多 180 秒，重试和消歧计入对应阶段；各阶段不自动互借。

执行规则：

1. 开发集完整运行并检查 20/20，包括所有预设断言、引用及运行指标；任何样本未过就停止，不调用留出。
2. 开发通过后，同一版本依次运行两组留出。语义错误可继续完成固定诊断集合；未知调用、预算或服务阻断暂停，未执行样本保留在分母中。
3. 新断言留出至少 18/20，且所有应出现断言和条件完整，无非预期待审、无虚构断言、无错误/未知断言被判 correct；关键未知边界不能误判 incorrect。
4. 完整评分 14/14 及 7 个对照关系全部符合冻结预期，仅允许浮点计算误差。
5. 用量、尝试与输入身份完整。停止或完成后恢复一次，验证已有终态不新增调用和结算；若有未完成但可恢复的回执，只复用该回执继续。
6. 任一验收未过，保留失败结果，不改 prompt、阈值或样本重跑，不创建新目录绕过停止规则。

## 10. 实施顺序与交付

顺序：保存 v5 工作区基线 → 定位模块 → 提取/证据接入 → 指标语义 → 恢复与门禁 → 离线回归 → v6 输入冻结 → 真实开发集 → 有条件执行留出 → 结果记录。

交付包含：

- 定位目录与规范输出合同、指标定义表、版本与兼容说明。
- 原文位置、重复出现、上下文、语义反例、恢复和门禁的测试证据。
- v5/v6 固定 20 个样本的逐项结果，并区分提取失败、定位歧义、证据关系错误、指标映射问题和 oracle 问题。
- 定位解析成功率、覆盖完整率、结构修复次数、实际补提取结果、各阶段 token/时间/未知预约及留出执行状态。
- 代码/离线验证、真实开发集、断言留出、完整评分和正式资格分别报告。
- 代码尚未提交时明确标注；需要后续提交同步的 CI 仍列为未验证项，PR 保持 Draft。
